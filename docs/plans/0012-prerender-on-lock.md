# 0012 — 锁定即预渲染：把最终渲染的等待压成打包时间

## 背景 / 问题

真实使用反馈（2026-08-26）：全部镜头评审完点「确认渲染」后等待太久。
原因显而易见 —— 所有片段的 ffmpeg 重编码都堆在最后一步串行执行，
一个十镜头的项目要等十次转码，而这期间用户只能干等。

用户的建议是「每个选中的镜头先做截取，然后再做渲染，最后打包下载」——
即把重活提前、按镜头拆开。本计划把它落成：**镜头一锁定就后台把该镜头
剪出来**；用户评审下一个镜头的那几十秒，正好是上一个镜头的转码时间。
评审结束时片段基本已经全在磁盘上，最终一步只剩核对与打包 zip。

### 为什么不是「先 -c copy 关键帧截取、再重编码」

拆成两步并不省时间：重编码耗时由**输出片段的时长**决定，与输入文件大小
基本无关（`-ss` 放 `-i` 前已是快速 seek）。纯 copy 截取虽然快，但关键帧
对齐会牺牲帧精确承诺、且无法烧 LUT。真正的时间来源是「把转码挪到用户
正在思考的时候做」，所以方案是并行化（预渲染），不是流水线拆步。

## 目标

- approve（锁定镜头）即入队 `shot_render` 任务，worker 立刻渲染该镜头的
  主选 + 备选片段到项目输出目录。
- 最终 `render` 任务逐项核对指纹，已有且入参未变的片段直接复用，
  只补漏 + 写 manifest + 打包。全部命中时最终等待 ≈ zip 时间。
- 换主意重锁（换候选/换滤镜）后旧产物自动作废重剪，不产生错内容。

## 非范围

- worker 多进程并行转码（单 worker 串行已够 —— 评审节奏天然错峰）。
- 渲染进度条（时间线事件已提供逐镜头提示）。

## 设计

- **指纹 sidecar**：每个片段旁写 `<文件名>.fp`，内容是入参哈希
  （素材路径/checksum、精确与含余量时码、滤镜 slug+checksum、CRF/preset）。
  「可复用」的唯一判据是指纹一致 —— 不依赖任何状态表，预渲染因此是
  **纯优化**：sidecar 丢了、指纹不匹配，最终渲染重剪即可，永不出错内容。
- **新任务种类 `shot_render`**（008 迁移，只改 job_run 的 kind 白名单）：
  params 带 project_id + shot_id，入队时 dedupe。执行时读最新锁定状态；
  镜头已被撤销锁定则静默跳过（队列竞态是常态不是故障）。
- **失败语义**：shot_render 失败只标 job 失败、不动项目状态 ——
  最终渲染会重剪同一片段，那才是有权判项目失败的路径。
- **时间线事件 `shot_prerendered`**：仅在真的剪出新片段时追加，
  纯缓存命中保持安静，避免刷屏。
- render_output 行仍只在最终渲染时写（它是交付留痕，不是缓存状态）。

## 验收标准

- 锁定镜头后 job_run 出现 shot_render 且成功；输出目录出现片段 + .fp。
- 全部锁定后点渲染：日志里 cached=True 占绝大多数，render_done 秒级到达。
- 重锁换候选/滤镜后最终渲染重剪该片段（指纹不同），内容正确。
- `make test` / `make lint` 全绿。

## 风险

- 用户反复重锁会产生废弃片段文件占盘 —— zip 只收计划内文件，正确性不受
  影响；输出目录按项目隔离，删项目目录即回收。
- 预渲染与最终渲染理论上可能并发写同一文件 —— 实际不会：单 worker 串行
  消费队列，shot_render 与 render 永不同时执行。多 worker 部署时需注意
  （目前不支持也不计划）。
