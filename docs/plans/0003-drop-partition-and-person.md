# 0003 — 去掉分区与 person，查询完全实时

- **状态**：已实现，待用真实数据验证
- **日期**：2026-08-10
- **取代**：[0002](0002-schema-and-batch.md) 里的分区方案与 [0001](0001-mvp.md) 里的两段式检索

## 触发

0002 实现了按 album 的 LIST 分区，同时我在交付时提了反对意见：这个量级不需要分区，
而分区会让主流程（查所有相册）变成对 N 个分区各扫一次再归并。这个意见被接受了。

同时确认了两个产品决定：

1. **不存 person 这类信息**。查询完全实时：上传自拍 → 检索 → 用完即弃。
2. 查询自拍**只取最明显的一张脸**做向量化，检索完成后要**明确告知用户自拍已删除**。

## 改了什么

### 数据模型

- `face` 从 LIST 分区表改回**普通表**，PK 回到单列 `id`。
- 删掉 `face.album`。album 只属于 `photo` —— 一张照片属于哪个相册是它自己的属性，
  与它上面有几张脸无关；`face` 通过 `photo_id` 外键间接得到。
  （原先 `face.album` 存在的唯一理由是「分区键必须在本表上」。）
- 删掉 `person` 表、`face.person_id`、SQL 函数 `ensure_face_partition`、
  `face_default` 分区、`album` 列上的 `COLLATE "C"`（那是为分区路由确定性加的）。
- `block_list` 的 scope 从 `person|photo` 改为 `face|photo`。
- `job_run.kind` 去掉 `cluster`。

### 检索

从两段式（簇心 → 簇内取图）改为**单段式**：

```
自拍 → 最明显的一张脸 → 对 face 做 KNN 取候选 → 阈值过滤 → 映射回照片 → 按最高分排序
```

配套改动：

- 删掉 `jobs/cluster.py`、`jobs cluster` 子命令、`make cluster`、CI 里的聚类步骤、
  `scikit-learn` 依赖、`PERSON_MATCH_THRESHOLD` / `CLUSTER_*` 配置。
- 新增 `SEARCH_CANDIDATES`（默认 500）。**这是新的召回上限**：pgvector 的 HNSW 只在
  `ORDER BY ... LIMIT n` 形式下会被用到，所以检索必须先取 N 个最近邻候选再过滤。
  某人照片数超过它就会被截断。带相册过滤时自动放大 4 倍（过滤发生在取候选之后）。

### 查询自拍只取一张脸

- `embedding` 服务的 `/extract` 新增 `primary_only` 参数。筛选发生在**识别前向之前**，
  所以其余人脸根本不会被向量化 —— 既省算力，也让离开该服务的人脸数据最少化。
- 判据是人脸框面积，`det_score` 作为并列时的次序。刻意不做更复杂的打分：
  这个选择直接决定查询结果，规则越简单越容易在出问题时说清原因。
- 多张自拍仍支持（最多 3 张），每张各取一张脸后取均值。这是**去掉聚类后唯一剩下的
  召回率提升手段**，所以 UI 继续鼓励多传一张，但不强制。

### 「自拍已删除」要让用户看见

- `POST /api/search` 响应新增 `selfie_discarded: true`。
- 前端新增 `DiscardNotice` 组件，检索结束后展示「你上传的自拍已从服务器删除，
  我们没有留底」。用 `role="status"` 而非 `alert` —— 这是正常完成的确认，
  不该打断屏幕阅读器正在播报的结果。

上传前的隐私说明是「我们打算怎么做」，这一行是「已经做了」。后者才是用户真正在意的
那个时刻，不能只写在文档里。

### opt-out 的重做

没有 person 表，「屏蔽某个人」就等于「屏蔽他的那一批 face」。新增：

```bash
make block SELFIE=/path/to/his-selfie.jpg
```

用当事人的自拍跑一次检索，把命中的 face 全部加进 `block_list`。命令**幂等**，
但**只覆盖当时库里的人脸** —— 新相册入库后需要再跑一次。这一点必须进运维流程，
否则 opt-out 会随时间悄悄失效。

## 代价（明确记录，不要当成 bug 排查）

| 代价 | 说明 |
| --- | --- |
| **侧脸/背光召回率下降** | 聚类原本能让侧脸经由同一个人的正脸被间接命中，现在没有这条路径。缓解手段只有「多传一张不同角度的自拍」 |
| **结果可能被候选数截断** | 某人照片数超过 `SEARCH_CANDIDATES` 时。调这个值，不要调阈值 |
| **相册过滤是后过滤** | 不再有分区裁剪。已用「候选数放大 4 倍」补偿，窄相册仍可能少返 |
| **opt-out 需要定期重跑** | 新照片入库后旧的屏蔽不覆盖它们 |

换来的：全库检索不受分区归并开销影响、schema 简单了一大截（少两张表两个函数）、
不落任何长期的人物身份数据。
