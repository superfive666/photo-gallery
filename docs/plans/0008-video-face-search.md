# 0008 — 视频人脸检索（提案，待批准后实施）

> 状态：**提案**。批准后按「迭代流程」实施；本文档先回答三个问题：
> 要不要新模型？改哪些地方？时间段怎么算出来、怎么搜出来？

## 目标

上传自拍（或浏览模式点脸）检索时，除了照片，还能返回**视频**，并给出
这个人出现的时间段列表：

```
某某视频（03:12–03:45、07:02–07:18 出现）→ 点击跳到源站视频对应时间点
```

## 一句话结论

**不需要部署任何新模型。** 视频就是按时间排列的一串图片：抽帧 → 走现有
embedding 服务（同一套 RetinaFace + ArcFace，同一个向量空间）→ 把逐帧检测
串成「时间段」→ 存进现有 `face` 表（加两个时间字段）→ 现有 KNN 检索天然
命中它们。新增的只有两样纯 CPU 的东西：**抽帧器**（PyAV，pip 装的 ffmpeg
封装）和**时间段聚合器**（几十行普通代码，不是模型）。

## 为什么不需要新模型

| 环节 | 需要什么 | 用什么 |
| --- | --- | --- |
| 视频解码/抽帧 | 不是模型 | PyAV（自带 ffmpeg 二进制，jobs 容器 pip 装即可） |
| 帧内人脸检测 | 检测模型 | **现有** det_10g（RetinaFace），帧=图片 |
| 人脸 embedding | 识别模型 | **现有** w600k_r50（ArcFace），**同一向量空间是关键** —— 自拍的查询向量可以直接和视频里的脸比 |
| 跨帧串联成时间段 | 不是模型 | IoU + 余弦相似度的贪心匹配（普通代码） |
| 检索 | 不是模型 | 现有 pgvector HNSW，一个索引同时覆盖照片和视频 |

市面上的「视频人脸检索」产品会加专用追踪器（ByteTrack）、行人重识别、
音频分析等 —— 在 1 fps 抽帧、社团活动视频的场景下全都是过度设计，
且行人重识别与本项目「不存人物身份数据」的立场直接冲突，明确不做。

## 核心设计

### 1. 抽帧：1 fps，帧当图片发给 embedding 服务

- 默认每秒抽 1 帧（`VIDEO_SAMPLE_FPS`，可调）。活动视频里一个人通常连续
  出现几秒到几分钟，1 fps 足够定位「哪段有他」；代价是 **短于 1 秒的一闪
  而过会漏**，这是已知取舍。
- 帧 JPEG 编码后走现有 `/extract/batch` —— **约束 #3 完好**：所有
  resize/对齐/归一化仍然只发生在 embedding 服务里，jobs 只做解码抽帧
  （解码不是识别预处理）。
- 视频先流式下载到临时文件再抽帧（几百 MB 的视频不能全放内存），
  处理完即删。「不缓存原图」的纪律指的是不做持久缓存，临时文件不违反；
  会写进计划的验收标准里（处理结束后临时目录必须为空）。

### 2. 时间段聚合：把逐帧检测串成 tracklet

对每个视频按时间顺序处理抽出的帧，每帧拿到若干 (bbox, embedding)：

```
对每个检测：
  在「活跃时间段」里找匹配 —— bbox IoU > 0.3 或 余弦相似度 > 0.6
  匹配上 → 并入该段（更新 t_end、累积 embedding）
  没匹配 → 开一个新段
超过 VIDEO_TRACK_GAP_S（默认 3 秒）没有新帧并入的段 → 关闭
关闭时：段的代表 embedding = 成员 embedding 的均值再 L2 归一化
        （与检索端多自拍取均值的做法一致）
```

1 fps 下人物移动可能让 IoU 失效，所以余弦相似度是主判据 —— embedding
本来就有，不用额外算。**一个 tracklet 不是「一个人」**：它是「一段时间内
连续出现的一张脸」，边界在单个视频内、有起止时间，语义上等同于
「一张照片上的一张脸」，不违反约束 #8（不存跨视频/跨照片的身份数据）。
转头、遮挡会把同一个人断成多段 —— 无害，前端把间隔 ≤2 秒的相邻段合并显示。

### 3. 存储：复用 `face` 表（004 迁移）

不建新表。`face` 表加两个可空字段，照片行恒为 NULL：

```sql
ALTER TABLE face ADD COLUMN t_start_ms INTEGER;   -- 视频 tracklet 的起点
ALTER TABLE face ADD COLUMN t_end_ms   INTEGER;   -- 终点
ALTER TABLE photo ADD COLUMN duration_ms INTEGER; -- 视频时长（ffprobe）
```

一行 = 一个 tracklet：`embedding` 存段代表向量，`bbox_*`/`face_px`/
`det_score` 存段内质量最好那一帧的值，`thumb` 从那一帧裁人脸小图
（**浏览模式的点脸检索对视频自动生效**，零额外工作）。

复用一张表的收益链很长，这是本方案最重要的决定：

- **一个 HNSW 索引、一次 KNN** 同时召回照片和视频段，不用两路查询再融合；
- 相似度阈值天然统一（同一向量空间）；
- `block_list` 对视频 tracklet 自动生效 —— opt-out 的人在视频里也被屏蔽；
- 按相册 scope、邀请码边界、审计，全部不用动。

容量：一个 5 分钟视频约 20–60 个 tracklet ≈ 二三十张照片的人脸行数，
不影响容量结论。

### 4. 检索：候选查询零改动，外层带回时间段

内层 `ORDER BY embedding <=> q LIMIT n` 一字不动（约束 #7）。外层：
照片仍按 photo 聚合取最高分；视频按 photo 聚合的同时把命中的段
`(t_start_ms, t_end_ms, sim)` 聚成数组返回。响应里视频匹配多带：

```json
{ "kind": "video", "duration_ms": 486000,
  "segments": [ {"start_ms": 192000, "end_ms": 225000, "score": 0.61} ] }
```

### 5. 前端：视频结果卡片 + 时间点直达

- 结果网格里视频卡片带时长角标和「出现时段」chips（`03:12–03:45`）；
- 点 chip → 打开源站视频并从该时间点开始：直链 mp4 支持
  `video.mp4#t=192` 片段标识，浏览器原生跳转，不需要自建播放器；
- 浏览模式里视频照片同列，点开视频显示 tracklet 人脸小图，点脸检索
  与照片完全同一条链路。

## 算力与耗时估算（RTX 3060 Ti 8GB）

- 检测 det_10g@640 批量 ≈ 25–40 帧/秒；识别批量吞吐远高于检测，不是瓶颈；
- 1 fps 抽帧：**10 分钟视频 ≈ 600 帧 ≈ GPU 上 20–30 秒**；解码（CPU）与
  推理（GPU）流水线并行，墙钟时间接近取大者；
- 一场活动 20 个 3 分钟视频 ≈ 3600 帧 ≈ **两三分钟处理完**。夜间定时
  ingest 完全吃得下，白天手动跑也不心疼。
- 显存：现有服务已在跑同样的批量推理，无新增压力。

## 风险与已知取舍

1. **短暂露脸（<1s）漏检** —— 1 fps 的固有代价。真发现不够再把
   `VIDEO_SAMPLE_FPS` 提到 2（成本线性翻倍），不需要改架构。
2. **视频画质**（运动模糊、压缩）让 det_score/face_px 普遍低于照片 ——
   质量门控沿用 `MIN_FACE_PX`，预期视频召回率低于照片，README 里如实写。
3. **tracklet 断段** —— 转头/遮挡断成多段，前端合并相邻段展示，无害。
4. **源站带宽与磁盘** —— 视频下载走现有限速；临时文件用完即删，
   加 `VIDEO_MAX_DURATION_S` 上限防超长视频拖垮任务。
5. **阈值** —— 同一向量空间，先沿用照片阈值；评估集加视频样本后用
   `make eval` 标定（评估流程现成）。

## 明确不做（与隐私立场绑定）

- 不做跨视频/跨照片的人物聚类或身份档案（约束 #8 不变）；
- 不做行人重识别（背影/衣着匹配）—— 超出「人脸检索」的授权预期；
- 不做音频/说话人识别；
- 不自建视频播放/转码 —— 原视频始终只是指向源站的 URL。
