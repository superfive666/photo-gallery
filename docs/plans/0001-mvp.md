# 0001 — MVP：自拍检索可用

> ⚠️ 本文件是历史记录。其中的 person 聚类与两段式检索已在 [0003](0003-drop-partition-and-person.md) 中移除。


- **状态**：进行中
- **日期**：2026-08-10

## 目标

社团成员能打开 `faces.zrc.sg`，输入邀请码，上传一张自拍，在 3 秒内看到自己出现在历史活动
相册里的照片网格，并能点开跳回 photos.zrc.sg 看原图。

## 范围

### 包含

1. **基础设施**：docker compose（db / embedding / api / web），迁移执行器，`.env.example`，Makefile。
2. **`embedding` 服务**：InsightFace buffalo_l，`POST /extract`，模型打进镜像，threadpool 推理，
   出口 L2 归一化。
3. **`jobs ingest`**：`SourceAdapter` 抽象 + `local_dir` 可用实现 + `static_gallery` 占位。
   幂等、增量、断点续跑、失败不中断、原图处理完即删、生成缩略图。
4. **`jobs cluster`**：DBSCAN 聚类成 person，算簇心。
5. **`api`**：邀请码换 session、`POST /api/search`（两段式检索）、缩略图分发、原图签名跳转、
   限流、上传防护。
6. **`web`**：单页 —— 邀请码门 → 隐私告知与同意 → 上传/拍摄自拍 → 结果网格 + lightbox。
   移动端优先，客户端预压缩。
7. **opt-out**：`block_list` 表 + 一条运维用的 CLI（不做 UI）。
8. **评估**：`jobs eval` + 评估集流程文档，产出首次标定的阈值。
9. **CI/CD**：`ci.yml`（GitHub 托管 runner）+ `deploy.yml` / `ingest.yml`（自建 runner）。

### 不包含（明确推迟）

| 项 | 推迟原因 |
| --- | --- |
| **视频处理** | 抽帧会让计算量和存储上一个量级。先确认 album 里视频占比再决定优先级 |
| **与 photos.zrc.sg 账号打通** | 邀请码足够满足第一期的访问控制需求，OAuth 对接工作量大 |
| **person 命名 / 人脸管理后台** | 检索不需要知道人名。加了反而扩大隐私暴露面 |
| **opt-out 自助 UI** | 第一期由管理员用 CLI 处理，量小 |
| **多语言 i18n** | 待确认是否需要 |
| **staging 环境** | 社团项目，带健康检查和回滚的单环境部署够了 |

## 关键风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **源站抓取方式未知** | 阻塞 M3 的真实数据 | 用 `local_dir` adapter 先把 M2~M7 全部跑通，源站只是最后换个 adapter。见 `docs/data-source.md` 的待答问题 |
| **召回率不达预期** | 项目没有实用价值 | 先做漏检归因（小脸/检测失败/相似度不足），按归因对症下药，别盲目调阈值 |
| **CPU 推理太慢** | 建库时间过长 | 先实测：buffalo_l 在 CPU 上约 0.1~0.3s/张，1 万张约 1 小时，可接受。不够则加并发或上 GPU |
| **自建 runner 安全** | 家用机器被入侵 | PR 的 CI 跑托管 runner，只有部署跑自建。见 `plans/0013`：公开仓库后已移除全部 workflow 与自建 runner |
| **隐私事故** | 不可挽回 | `CLAUDE.md` 的硬性约束 + `test_no_persistence.py` 把「自拍不落盘」变成会失败的测试 |

## 下一次迭代的候选

按预期价值排序，待 MVP 上线后根据实际使用情况重排：

1. 视频抽帧（取决于 album 里视频占比）
2. 与源站账号打通 + album 级可见性过滤
3. opt-out 自助页面
4. 「这不是我」反馈按钮 → 收集困难样本用于阈值再标定（这是最便宜的持续改进手段）
5. 结果按活动分组 / 时间轴视图
6. GPU 推理
