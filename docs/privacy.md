# 隐私与合规

人脸数据是本项目唯一真正危险的部分。技术上出错可以回滚，隐私上出错不能。

## 数据分类

| 数据 | 性质 | 存储 | 留存 |
| --- | --- | --- | --- |
| 源站照片的人脸 embedding | **生物识别数据** | `face.embedding`（Postgres） | 长期，直至 opt-out 或项目下线 |
| 照片缩略图 | 个人数据 | `photo.thumbnail` | 同上 |
| **用户上传的自拍** | **生物识别数据** | **不存储** | **请求结束即销毁** |
| 检索行为 | 使用日志 | `search_audit`（只有计数与耗时） | 30 天 |

## 硬性规则

1. **自拍绝不持久化。** 不落盘、不落库、不写日志、不进 APM/错误上报的附件。
   字节只存在于 FastAPI 请求生命周期内的内存中，函数返回即失去引用。
   → 对应 `CLAUDE.md` 约束 #1，代码里有对应测试 `api/tests/test_no_persistence.py`。
2. **embedding 与人脸图片不进日志。** 日志只允许 id、计数、耗时、错误类型。
3. **EXIF 在推理前剥离**，包括 GPS。
   另外查询自拍只取最明显的一张脸，背景里其他人的脸根本不会被向量化。
4. **源站是公开的，但这不降低本项目的义务。** photos.zrc.sg 无需鉴权即可浏览，
   所以没有 private album 要过滤，也不需要签名链接。但**人脸检索创造了一个源站本身
   没有的能力**：源站上要找某人的照片得一张张翻，而这里输入一张自拍就能把他在所有活动
   里的照片一次性聚齐。可及性的量变就是隐私上的质变 —— 这是邀请码存在的全部理由。

## 法律框架（新加坡 PDPA，兼顾成员在海外时的 GDPR）

本项目处理的是可识别自然人的生物特征数据，属于 PDPA 下的个人数据，需要满足：

- **同意（Consent）**：首次使用前展示明确告知并要求勾选同意。文案要说清：
  处理什么、为什么、存多久、怎么删除。同意记录留存。
- **目的限定（Purpose Limitation）**：仅用于「让本人找到自己的活动照片」。
  不得用于统计出勤、识别陌生人、对外提供。
- **访问与更正（Access & Correction）**：成员可查询自己有哪些数据、可要求删除。
- **保护（Protection）**：见下方安全措施。
- **保留限制（Retention Limitation）**：项目下线或成员退出时删除其 embedding。

> 我不是法律顾问。上线前建议由社团负责人确认一次告知文案与同意流程。

## Opt-out 机制

必须在第一期就做，不能推迟 —— 这是同意机制的配套设施，缺了它同意就是空的。

因为**不存 person**，「屏蔽某个人」就等于「屏蔽他的那一批 face」。
`block_list` 表支持两种粒度：

- **按 face**：某成员声明「不希望被检索」。管理员用他的自拍跑一次：

  ```bash
  make block SELFIE=/path/to/his-selfie.jpg
  ```

  命令会检索出全部命中的 face 并逐一加入屏蔽名单。这条命令**幂等**，可以重复运行；
  但它只覆盖当时库里的人脸，**新相册入库后需要再跑一次** —— 这一点必须写进运维流程，
  否则 opt-out 会随时间悄悄失效。
- **按 photo**：单张照片不希望出现在检索结果中（`jobs block --photo <uuid>`）。

屏蔽在 SQL 层过滤，而不是在应用层结果集里过滤 —— 后者容易在新增查询路径时被漏掉。

成员要求彻底删除而不只是屏蔽时，直接 `DELETE FROM face WHERE id = ANY(...)`，
embedding 就物理消失了。

## 滥用风险与对策

**核心风险：** 任何人拿到一张他人的照片，上传后即可获得该人出现在全部活动中的所有照片，
包括提交者本不该看到的场合。这是这类系统的固有滥用面，不是假想。

对策：

| 风险 | 对策 |
| --- | --- |
| 陌生人扒某人的照片 | 邀请码限制访问，仅社团成员可用。源站公开只意味着「照片本身可见」，不意味着「可以被按人聚合」 |
| 成员滥用（搜别人） | 技术上无法根治（无法验证「这是你自己」）。做限流 + `search_audit` 留痕 + 明确的使用条款 |
| 暴力枚举 | 按 session + IP 双维度限流，超限指数退避 |
| 邀请码泄露 | 邀请码可轮换；session 短有效期；异常访问量告警 |
| 数据库被拖走 | embedding 不可逆推出原图，但可用于跨库比对 → 磁盘加密 + 备份加密 + 最小暴露面 |
| 有人直接爬源站自建一套 | 技术上无法阻止（源站公开）。这不是不做访问控制的理由 —— 我们只对自己提供的能力负责 |

**活体检测（liveness）不在范围内。** 它无法阻止「上传别人的照片」这一主要滥用方式
（照片翻拍很容易绕过），投入产出不划算。靠访问控制 + 留痕 + 条款约束更实际。

## 安全措施清单

- Postgres 不暴露到宿主机以外，仅 compose 内网可达。
- `photo.thumbnail` 是唯一存在本项目里的照片内容（256px 缩略图）。原图始终只是一个
  指向源站的 URL，我们不复制、不缓存原图。
- 上传：大小上限、真实 MIME 嗅探、`Image.MAX_IMAGE_PIXELS` 防解压炸弹。
- session cookie：`HttpOnly` + `Secure` + `SameSite=Lax`，短有效期。
- 全站 HTTPS，HSTS。
- 备份加密，且**做过一次恢复演练**（未演练的备份等于没有备份）。
- 依赖漏洞扫描进 CI。

## 用户可见文案（前端需实现）

上传区附近必须常驻，不能藏在折叠里：

> 你的自拍仅用于本次检索，处理完成后立即从内存中销毁，不会被保存到任何位置。
> 照片库中的人脸特征数据用于匹配，你可以随时申请将自己从检索中移除。

首次使用需勾选同意；`/privacy` 页面提供完整说明与联系方式。

**检索完成后还要再确认一次**（`DiscardNotice` 组件，由响应里的 `selfie_discarded`
驱动）：

> ✓ 你上传的自拍已从服务器删除，我们没有留底。下次检索需要重新上传。

上传前的说明是「我们打算怎么做」，检索后的这一行是「已经做了」—— 后者才是用户真正
在意的那个时刻，不能省。
